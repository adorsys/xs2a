== Verification of Payee (VOP) Service
:toc-title:
:imagesdir: ../usecases/images
:toc: left

toc::[]

The Verification of Payee (VOP) service is a mandatory service for `instant payment` and optional service for other payment types at the XS2A interface that allows TPPs to verify beneficiary account details before initiating a payment.
This service helps prevent fraud and misdirected payments by confirming that the account holder name matches the provided account identifier (IBAN).

*Note:* VOP services do NOT require Strong Customer Authentication (SCA) as they are read-only verification operations that do not transfer funds or access sensitive account information.

=== VOP Service Variants

According to the Berlin Group NextGenPSD2 Framework version 1.3.15, two VOP service variants are defined:

* *DEDICATED* - VOP service provided through dedicated endpoints separate from payment initiation
* *INTEGRATED* - VOP verification integrated within the payment initiation flow (not yet implemented in our XS2A)

XS2A currently implements the *DEDICATED* variant. The INTEGRATED variant is configured but not yet fully implemented; no integrated payment-flow endpoints are exposed at this time.

=== VOP API Reference

XS2A implements VOP services according to:

* *Berlin Group NextGenPSD2 Framework* version 1.3.15

=== The Current version of VOP Supports the dedicated variant with the following endpoints:

|===
|Endpoint | Method | Purpose | Implementation Status

|`/v1/verification-of-payee`
|POST
|Submit a single party verification request
| Implemented via `SingleVopSpi.performVerification()`. Requires `partyAccount` and optional `party` identification; response contains `partyNameMatch`/`partyIdMatch`.

|`/v1/bulk-verification-of-payee`
|POST
|Submit multiple party verification requests
| Implemented via `BulkVopSpi.performVerification()`. Returns HTTP 201 with `partyVerificationResponses` when processed synchronously, or HTTP 202 with `vopBulkId` when deferred (async mode not yet implemented).

|`/v1/bulk-verification-of-payee/{vopBulkId}`
|GET
|Retrieve full verification requests and results for a bulk submission
| Implemented via `BulkVopSpi.getBulkVopById()`. Response body contains `partyVerificationRequestsAndResults` with complete request and result data.

|`/v1/bulk-verification-of-payee/{vopBulkId}/status`
|GET
|Retrieve only the current bulk status (lightweight polling endpoint)
| Implemented via `BulkVopSpi.getBulkVopStatusById()`. Returns `vopBulkId` and `vopBulkStatus` only (optimized for polling without loading full verification results).
|===

=== Single Verification Flow

image::vopSingleVerificationDedicated.png[Single VOP Dedicated, align="center"]

*Endpoint:* `POST /v1/verification-of-payee`

*Request Example:*
[source,json]
----
{
  "partyAccount": {
    "iban": "DE02100100109307118603"
  },
  "party": {
    "name": "Peter Miller Ltd"
  }
}
----

*Response Example (Name Match):*
[source,json]
----
{
  "partyNameMatch": "MTCH"
}
----

*Response Example (Identification Match):*
[source,json]
----
{
  "partyIdMatch": "MTCH"
}
----

==== Verification Results

The VOP service can return the following verification results:

* *MATCH* - Account holder name matches exactly with the provided name
* *NO_MATCH* - Account holder name does not match the provided name
* *PARTIAL_MATCH* - Account holder name partially matches (fuzzy matching)
* *NOT_AVAILABLE* - Verification service is temporarily unavailable

==== Bulk VOP Status Codes

The bulk VOP service uses the following status codes to indicate processing state:

* *received* - Bulk request has been accepted but not yet processed
* *processing* - Processing is in progress (technical validation)
* *completed* - All verifications completed successfully
* *rejected* - Bulk request has been rejected

NOTE: The actual status values returned are: `received`, `processing`, `completed`, `rejected` (not the ISO20022 codes RCVD/ACTC/ACSC/RJCT).

=== Processing Modes Configuration

The ASPSP can configure which bulk processing modes are supported:

[source,yaml]
----
vop:
  bulkBatchProcessingSupported:
    - synchronous-mode   # Immediate processing, results in response
    - asynchronous-mode  # Deferred processing, results via GET request
----

*Synchronous Mode* is recommended for:

* Small batches (< 100 verifications)
* Real-time payment flows
* Interactive user interfaces

*Asynchronous Mode* is recommended for:

* Large batches (100+ verifications)
* Background batch processing
* Non-interactive workflows

=== Security Settings for VOP

[source,yaml]
----
security:
  SigningHttpMessageSupported: FALSE   # disables x-jws-signature, Digest validation( Set to false because it is not yet implemented)
  SecuringBodyMessageSupported: FALSE  # disables Body-Sig-Profile / Body-Enc-* headers ( Set to false because it is not yet implemented)
----

When set to TRUE, the corresponding headers must be supplied and validated per BG 11d.

=== VOP Architecture

==== Layer Overview

image::vopArchitectureLayerOverview.png[VOP Architecture Layer Overview, align="center"]

==== Controller Layer

*VopController* (`de.adorsys.psd2.xs2a.web.controller.VopController`)

Responsibilities:
* HTTP request/response handling
* TPP certificate validation (eIDAS QWAC)
* Request ID validation
* Request body JSON schema validation
* Delegation to service layer

Key endpoints:
* `POST /v1/verification-of-payee` - Single verification
* `POST /v1/bulk-verification-of-payee` - Bulk verification
* `GET /v1/bulk-verification-of-payee/{bulkVopId}` - Bulk status

==== Service Layer

*VopService* (`de.adorsys.psd2.xs2a.service.VopService`)

The VopService orchestrates the verification process by:

1. Recording the incoming request event
2. Validating the request (supported variants, endpoint format, request body)
3. Delegating to the appropriate create/read service
4. Returning the verification response

The service handles three main operations:

* *Single Verification* - Delegates to `CreateSingleVopService`
* *Bulk Verification* - Delegates to `CreateBulkVopService` (sync mode only)
* *Bulk Retrieval* - Delegates to `ReadBulkVopService` or `ReadBulkVopStatusService`

NOTE: The service validates that the DEDICATED variant is configured before processing any request.

==== SPI Layer

*VopSpi* (`de.adorsys.psd2.xs2a.spi.service`)

Interface that ASPSPs must implement. The VOP SPI layer consists of three interfaces:

*Base Interface - VopSpi:*
[source,java]
----
public interface VopSpi<T extends SpiVop, R> {
    @NotNull
    SpiResponse<R> performVerification(@NotNull SpiVopContextData vopContextData, @NotNull T vop);
}
----

*Single Verification - SingleVopSpi:*
[source,java]
----
public interface SingleVopSpi extends VopSpi<SpiSingleVop, SpiSingleVopInitiationResponse> {
    @NotNull
    @Override
    SpiResponse<SpiSingleVopInitiationResponse> performVerification(
        @NotNull SpiVopContextData vopContextData,
        @NotNull SpiSingleVop singleVop
    );
}
----

*Bulk Verification - BulkVopSpi:*
[source,java]
----
public interface BulkVopSpi extends VopSpi<SpiBulkVop, SpiBulkVopInitiationResponse> {
    @NotNull
    @Override
    SpiResponse<SpiBulkVopInitiationResponse> performVerification(
        @NotNull SpiVopContextData vopContextData,
        @NotNull SpiBulkVop bulkVop
    );

    @NotNull
    SpiResponse<SpiGetBulkVopResponse> getBulkVopById(
        @NotNull SpiVopContextData spiContextData,
        @NotNull String vopId
    );

    @NotNull
    SpiResponse<SpiGetBulkVopStatusResponse> getBulkVopStatusById(
        @NotNull SpiVopContextData spiContextData,
        @NotNull String vopId
    );
}
----

*SPI Implementation Requirements:*

The ASPSP must implement the SPI interfaces to:

* Query account database for account holder details
* Perform name matching (exact, fuzzy, or phonetic)
* Generate appropriate verification results
* Return status reason codes for failures
* Handle bulk processing (synchronous mode)

=== Configuration Reference

Complete ASPSP Profile configuration for VOP:

[source,yaml]
----
# VOP Service Configuration
vop:
  # API Framework Reference
  vopxReference:
    apiName: NextGenPSD2
    apiDocument: https://www.berlin-group.org/nextgenpsd2-downloads
    apiVersion: 1.3.15

  # Supported VOP Service Variants
  variantSupported:
    - DEDICATED        # Standalone VOP endpoints (implemented)
    # - INTEGRATED     # VOP in payment flow (not yet implemented)

  # Bulk Processing Modes
  bulkBatchProcessingSupported:
    - synchronous-mode   # Immediate processing with results in response
    - asynchronous-mode  # Background processing with GET status endpoint

# Security Settings (added for VOP)
security:
  # HTTP Message Signing
  # When FALSE: x-jws-signature and Digest headers not validated
  # When TRUE: TPPs must sign HTTP messages
  SigningHttpMessageSupported: FALSE

  # HTTP Body Signing/Encryption
  # When FALSE: Body-Sig-Profile, Body-Enc-Profile, Body-Enc-List not processed
  # When TRUE: TPPs can sign/encrypt request body fields
  SecuringBodyMessageSupported: FALSE
----
